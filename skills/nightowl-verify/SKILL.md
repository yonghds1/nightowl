# Nightowl Verify — 独立机器门禁验证与仲裁技能

本技能负责在实现代码交付后、合并至主分支前，执行严格的独立机器验证。

触发时机：任务实现完成待合并、重试排错、或代码审查前进行客观事实核验。

## 核心职责与执行契约

1. **自动寻址与执行**：
   运行标准命令：
   ```bash
   nightowl verify --id <id>
   ```
   CLI 优先使用已存在的 `.nightowl/worktrees/<id>`；不存在时在调用目录执行预设门禁，混合工作区应从根目录调用。如需手动指定执行目录，可使用 `--cwd <dir>` 选项。

2. **严格判定原则**：
   - 机器验证严格以命令退出码为唯一准绳（`exit code === 0` 即为通过，非 0 即为失败）；
   - 不进行任何不可靠的文本正则猜测，杜绝把 `tsc --noEmit`、`eslint` 等无计数命令误判为失败。

3. **失败落盘结构化反馈 (`feedback.json`)**：
   若门禁命令失败，系统自动提炼纯净错误摘要，并写入：
   ```
   .nightowl/tasks/<id>/feedback.json
   ```
   实现代理应直接读取该文件中的 `command`、`exitCode` 与 `diagnostic` 关键段落进行针对性排错，禁止盲目反复重试。

4. **成功回执与单仓库版本绑定**：
   所有门禁通过后记录命令结果；能够取得目标 Git 版本时额外记录：
   - `head`：当前工作区的精确 `git rev-parse HEAD` 哈希；
   - `dirty_diff_hash`：工作区状态指纹。
   
   单仓库执行 `nightowl worktree merge <id>` 时，比对分支 HEAD 与已有回执 HEAD，验证后新增提交会阻断合并并要求重新验收；合入后默认重跑门禁。不能将状态指纹视为完整文件内容快照。非 Git 根目录没有统一 HEAD，按下方限制执行。

## 混合工作区验收

从选定根目录运行 `nightowl verify --id <id>`；门禁明确子目录，例如 `cd "repo a" && npm test`。非 Git 根目录无统一 HEAD，验收仍记录命令结果并明确告警，不能声称已绑定各子仓版本。验证后逐仓检查提交状态再审查；缺乏统一版本绑定不等于允许跳过真实验收。
