# Nightowl Verify — 独立闭环验证与仲裁技能

本技能负责在实现子代理交付代码后、合并至主分支前，执行严格的独立机器验证与仲裁。验证绝不仅是运行一条退出码为 0 的命令，而是一套多维立体防御机制。

触发时机：任务实现完成待合并、重试排错、实现与审查结论不一致需要争议仲裁时使用。上游由 nightowl-plan 拆出带验收命令的任务，nightowl-run 调度执行，本技能给出是否可合并的客观判定。

## 核心职责与工作流

1. 按快到慢的顺序执行分级门禁，任何一级失败立即短路，不跑后续重型测试。
2. 在隔离工作区中验证新代码，杜绝验证对象错位（验到主仓旧代码）。
3. 识别空测试与恒真测试，防止模型用虚假全绿蒙混过关。
4. 提炼纯净错误诊断，写入结构化反馈，指导实现子代理定向修正。
5. 当机器验证与人工审查结论冲突时，给出中立仲裁裁决。

标准闭环：

```
实现 → 审查 → 验证 → 提交 → 合并
```

验证通过是合并的前置条件。验证失败则打回实现，耗尽重试预算则标记阻塞。

## 多级阶梯门禁测试

任务的验收命令在建任务时写入，按快到慢排列。验证按 L0 到 L3 逐级推进：

| 门禁 | 目标 | 典型命令来源 |
|------|------|--------------|
| L0 语法 | 毫秒级过滤破损代码 | 任务验收命令第一条 |
| L1 类型 | 秒级捕获类型与编译错误 | 任务验收命令第二条 |
| L2 目标单测 | 验证本次需求的新测试真实通过 | 任务验收命令中的目标单测 |
| L3 影响域回归 | 确认未破坏既有基线功能 | 任务验收命令中的回归测试 |

执行原则：

- L0 失败立即打回，不浪费时间跑 L3。
- L1 失败只看类型错误定位，不翻全量日志。
- L2 必须命中本次需求的新增断言，只跑存量全量测试不算过关。
- L3 基于变更涉及的核心模块执行反向依赖测试。

验收命令的维护方式：在建任务时用带验收命令的方式写入，后续按项目实际技术栈调整。查看当前任务的验收命令：

```
nightowl --dir <项目根目录> status
nightowl next
```

## 隔离环境验证调用规范

跨工作区路径错位是最高频的验证事故。子代理在隔离 worktree 里写代码，任务池只在主仓。必须显式指定验证的工作区，不能依赖默认当前目录。

在主仓对指定隔离区执行验证：

```
nightowl verify <id> --cwd <dir>
```

主仓路径显式指定时的完整写法：

```
nightowl --dir <项目根目录> verify <id> --cwd <worktree路径>
```

规范：

- `<dir>` 指向该任务的隔离 worktree 路径。
- 禁止切到主仓直接验证 worktree 的代码，禁止在 worktree 里找不到任务池时硬跑。
- 合并前用 `nightowl worktree list` 确认隔离区仍在，合并后成对执行合并与清理：

```
nightowl worktree merge <id>
nightowl worktree cleanup <id>
```

隔离区的新建与复核：

```
nightowl worktree setup <id>
nightowl worktree list
```

残留先回收再验证，验证只认隔离区内的新代码。

## 防模型作弊与空测试检查

以下行为一律判验证不通过，打回实现：

1. 空测试：新增测试文件无断言，或断言数量为零。
2. 恒真测试：断言恒为真，例如断言 true 等于 true，与需求无关。
3. 全跳过测试：用例全部跳过，输出全绿但零执行。
4. 旧码验证：验证时工作区不含本次改动，测的是主仓旧代码。
5. 删断言过关：通过删除失败断言而非修复代码来变绿。

检查方法：

- 看变更是否包含针对当前需求的新增断言。
- 看测试报告的执行数与跳过数，零执行即作弊。
- 看主分支是否含有带标记的提交，未合入就声称完成即虚假完成。
- 有验收命令的任务，在记录完成前校验是否已验证通过，无验证记录不得标记完成：

```
nightowl verify <id> --cwd <dir>
nightowl done <id> <actual_min>
```

重试耗尽仍失败则标记阻塞，不无限重试：

```
nightowl block <id>
```

## 智能语义错误提取与 feedback.json 规约

禁止把原始超长日志整段塞回模型。验证失败时按以下规则提炼诊断：

- 总长度 2000 字符以内整段返回，不做任何切割。
- 超长时保留尾部 30 行，并补充命中关键词的关键行段落。
- 关键词：FAIL、ERROR、Error:、Failed:、AssertionError。
- 关键行取前后各 1 行上下文，最多 15 行。
- 自动剔除框架内部堆栈，只留文件、行号、断言差异。

提炼后的诊断写入结构化反馈，路径为任务目录下的反馈文件：

```
.nightowl/tasks/<assignee>/<task_dir>/feedback.json
```

字段规约：

```json
{
  "version": 1,
  "task_id": "T1",
  "attempt": 2,
  "max_budget": 3,
  "status": "NEED_REVISION",
  "failure_type": "TYPE_ERROR",
  "diagnostics": {
    "gate": "l1_typecheck",
    "command": "npm run typecheck",
    "exit_code": 2,
    "distilled_errors": [
      {
        "file": "src/state.ts",
        "line": 42,
        "column": 15,
        "code": "TS2339",
        "message": "Property verification does not exist."
      }
    ],
    "clean_snippet": "src/state.ts:42:15 error TS2339"
  },
  "oscillation_guard": {
    "detected": false,
    "current_patch_hash": "e3b0c44298fc1c149afbf4c8996fb92427ae41e4649b934ca495991b7852b855",
    "previous_patch_hashes": [
      "d41d8cd98f00b204e9800998ecf8427e"
    ]
  },
  "recommended_actions": [
    "补齐缺失的类型字段定义",
    "不要回滚上一轮已通过的类型守卫修改"
  ]
}
```

反震荡守卫：每轮失败计算当前补丁哈希并与历史比对。若发现当前补丁与更早某轮完全一致，判定为方案倒退，立即中断盲目重试，要求开辟新假设方案，防止在互斥状态间反复横跳耗尽预算。

## 实现与审查争议仲裁

当代码审查与机器验证结论不一致，或子代理对验收标准存在分歧时，由本技能仲裁。仲裁只认三样证据：任务验收标准、代码变更、验证日志。

仲裁流程：

1. 重跑隔离验证，以机器结果为基准：

```
nightowl verify <id> --cwd <dir>
```

2. 读取审查结论与任务状态：

```
nightowl review <id> --result PASS --level full
nightowl --dir <项目根目录> status
```

3. 综合三样证据给出裁决：
   - 验证失败而审查通过：以验证为准，打回实现，审查结论作废。
   - 验证通过而审查失败：按审查指出的问题定位逐条复核，属实则打回。
   - 双方都通过：允许进入提交与合并。
   - 双方分歧且证据不足：补跑目标单测与回归测试后再裁决。

裁决输出要求：结论先行，通过或打回只给一个；打回必须给出文件与行号定位及修复建议；不得同时要求两个互斥的修改方向。

## 失败处理与重试纪律

- 单轮失败只改一个假设，不批量试错。
- 同一补丁哈希出现两次即停手，换方案再试。
- 重试预算耗尽立即标记阻塞并写清原因，不静默丢弃代码。
- 阻塞前确认隔离区改动已保留，可用 sweep 巡检残留：

```
nightowl sweep
nightowl block <id>
```

收尾时验证记录、审查记录、提交标记三者对齐才算闭环完成。对账以任务池状态与代码提交为准，报告只做汇总展示：

```
nightowl --dir <项目根目录> report
```
